# 047D - CLI transport, Claude Code images and stale read blockers

Runtime 0.9.48 and the iteration identity come from `release.json`.

- **Principal focus:** phase **D** (design agents).
- **Milestones addressed:** D.02 and D.04, which remain **Parcial**.
- **Evidence:** the scopes below are **Verificado no escopo local**, as described
  under Verification. That means a local MinGW diagnosis build with the
  unpatched OCCT SDK. GitHub Actions did not run; the repository had no Actions
  minutes available. No performance, cost or design-quality claim is made.

All three changes come from one live Studio Team session on 046B: an engineer on
Claude Code, about 10 minutes of work, 25 attributed actions and 3 committed
steps. Only aggregate observations are kept here. The user's design was not
edited, saved, committed or packaged.

## Claude Code and Grok Build stdio transport (D.02)

**Observed failure.** A Studio Team engineer on the Claude Code CLI committed
a 29-command `doc_apply` (revision 4 at 08:37:18 UTC). About 90 s later the
role ended with:

> Claude Code stdin write was cancelled, disconnected or timed out; prior host receipts remain authoritative.

- The CLI wrote nothing to stderr and Windows recorded no crash.
- 90 s is the default `timeoutSeconds`.
- The evidence was read live through `studio_team_diagnostics`, `history_info`
  and `activity_info`, all read-only. The user's design was not modified.

**Cause.** One thread both executed the tool and wrote the reply into the CLI's
stdin, and neither step read the CLI's stdout. The pipes use the default buffer
size, and the CLI runs with `--verbose --include-partial-messages`, so it keeps
writing while a tool runs:

1. The CLI's stdout pipe fills and the CLI blocks writing.
2. Blocked, the CLI stops reading stdin.
3. ARK blocks writing a reply larger than the stdin buffer.
4. Both wait until the timeout terminates the job.

This explanation is inferred from the timing and the code; the CLI's internals
were not observed. The existing native test used a quiet fake CLI and small
replies, so it never reached this state.

**Fix.**
- **Reader thread.** `assistant_child_stdout.inl` drains stdout on a dedicated
  thread for both the Claude Code and Grok Build ACP channels. At most the
  configured response bound (`maxResponseBytes`) of unread bytes is held; past
  it, the reader waits for the consumer instead of growing.
- **Packet handling and exit detection** are unchanged.
- **Error messages.** A stdin write failure now names its cause: cancelled,
  timed out (the CLI read no input for the timeout and was stopped) or
  disconnected.

**Environment.** Studio launched from a Claude Code IDE terminal passed that
session's markers to the role CLI, because only 4 names were filtered:
- `CLAUDE_CODE_SESSION_ID`
- `CLAUDE_PID`
- `CLAUDE_CODE_MESSAGING_SOCKET` and its token
- several SDK-host feature flags

These are now dropped, together with every `CLAUDE_CODE_SESSION_*` and
`CLAUDE_CODE_MESSAGING_*` name. User sign-in and routing variables still pass.
[Claude Code connection](../CLAUDE_CODE_CONNECT_044B.md).

## Claude Code image input (D.04)

**Before.** With the Claude Code connector, an attached reference image failed
with:

> This connector explicitly does not support image input.

The route had been marked as not qualified, and the connector dialog stored
`image_input_supported:false`.

**Now.**
- Inline user images (Attach image, Inspire design, Image to CAD and steering
  images) travel as stream-json `image` blocks in the same user turn.
- The JSON text keeps an `attached_image N` placeholder.
- Data is validated as PNG or JPEG through the shared vision helpers: at most
  4 MiB each, 20 per prompt, never fetched, dropped or recoded.
- Saved Claude Code settings are migrated to the image route when loaded.
- Tool-result images such as `snapshot` are still not converted on this route.
- The Grok Build route is unchanged and still rejects images.

**Live check.** One live probe with Claude Code 2.1.304 (`haiku`) answered
`red` for a 64×64 red PNG sent in this format. This verifies the wire format,
not image-guided design quality.

## Stale rejected-read blockers (D.02)

**Observed failure.** In the same session, a `query_batch` row
`frame_inspect {id:2}` was rejected with `QUERY_BATCH_ROW_TOO_LARGE` (3967 >
`max_bytes` 3000) at revision 2. The engineer then removed feature 2, a
two-member probe frame, at revision 3. Afterwards:

- Studio kept showing "Unresolved tool requests: 1".
- `team_progress.next_action` kept returning `repair_failed_operation` for a
  feature that no longer existed.

A rejected read clears only after a later successful read with the same tool
and arguments, or an explicit `read_resolutions` report with same-tool
evidence. Neither is possible for a deleted subject. It never blocked
completion, because read failures do not block by default.

**Fix.** A committed `doc_apply` or `team_apply_step` that removes a feature
with a numeric `feature.remove` id supersedes every role's rejected reads of
that feature.

- **Tools covered:** read tools whose numeric `id` names a feature, meaning the
  `*_inspect` tools plus `sheet_preview`, `stock_preview`, `geometry_query`,
  `mesh_get`, `mesh_raycast` and `reference_navigate`.
- **Visibility:** each supersession is reported, not silently erased. The
  committing receipt carries `team_progress.read_resolutions` with
  `resolution_source:"subject_removed"`, `removed_feature_id` and
  `committed_revision`, and the team event log records it.
- **Not covered:** reads of surviving features and removals by name.

**Query shape hint.** `QUERY_BATCH_ROW_TOO_LARGE` already listed top-level
`result_keys`. It now also names one level of child keys for object fields (up
to 32). In the session above, the engineer guessed `topology.faces` after a
`reference_inspect` row of 63 KB; the child names (`references`,
`reference_capacity`, …) now appear in the first rejection.
[Tool layer](../AGENT_TOOL_LAYER_042D.md).

## Limits

- The transport fix removes the stdout back-pressure deadlock. It does not
  change the 90 s per-write and inactivity timeouts, and it does not make a
  silent CLI respond.
- Subject removal is recognised only from numeric `feature.remove` ids in the
  committed recipe. Removal by name, cascades and removals made outside the
  team (for example in Studio) do not supersede a rejected read.
