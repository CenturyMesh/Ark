# 049A - derived bakes and journal migration

Runtime 0.9.50 and the iteration identity come from `release.json`. Phase **A**
(trust) is the principal focus. Milestones **A.02** and **C.04** remain
**Parcial**.

The scopes below are **Verificado no escopo local**, as described under
Verification. That means a local MinGW diagnosis build with the unpatched OCCT
SDK; GitHub Actions did not run. No performance claim is made beyond the bytes
measured below.

## Observation

A Team session reached the 4 MiB logical document limit with only 36
iteration-journal nodes. After that, every further edit was rejected, and even
a later save was refused.

Read-only measurements on that document:

| What | Size |
|---|---|
| Logical document | 4,053,697 of 4,194,304 bytes |
| Journal | 3.76 MB |
| Bakes of the 3 motions | 906 KB of the current authoring |
| Per-instance frames inside those bakes | 882 KB (97%) |
| Motion graphs that generate them | 2.3 KB in total |

Every re-bake stored another copy of the derived frames in the journal. Only
aggregate figures are recorded here; the user's document was not edited,
committed or packaged.

## Change

**Bakes become receipts.**
- `motion.bake` stores a receipt: the 044B bake without the frame and
  coordinate payloads, plus `frames_sha256` and `coordinates_sha256`.
- Staleness still comes from `graph_digest`, `source_digest` and
  `source_revision`.

**Where frames come from**, in this order:
1. A bounded process cache.
2. The optional `ark_derived` container section.
3. A deterministic re-bake, which must reproduce the receipt digests.

A mismatch is reported as unverified and is never shown as the recorded bake.
`visualize_render` rejects unverified frames, and clearance checks its re-solve
against the digests.

**Existing documents.**
- Opening a document rewrites neither its authoring nor its journal.
- Inline frames stay playable.
- The next bake writes a receipt.

**Journal migration.**
- `history_migrate_derived{path,expected_revision,confirm:true}` is explicit
  and needs confirmation. Studio offers it as "Reclaim baked frames" in the
  Persistent iterations dialog.
- It first writes a verified backup beside the saved document,
  `<stem>.pre-049A.ark`, and never overwrites an existing file.
- It rewrites every journal state without the payloads and keeps branches and
  node metadata.
- It records `migrations[]` with the actor, counts, bytes and the backup.
- Migrated journals use `schema:2`.

**Formats and limits.**
- Document format 49 is selected only by receipts.
- The tool catalogue grows to 107.

**Frame-step rejection.** `MOTION_FRAME_STEP_TOO_LARGE` now reports the
channel, the frame, the largest step and `required_fps` (every step at or below
170°). Raising the fps no longer grows the journal.

See [derived bakes](../DERIVED_BAKES_049A.md),
[iteration history](../ITERATION_HISTORY.md) and [formats](../FORMATS.md).

## Measurement

Synthetic kiosk-like fixture (15 parts, 3 motions, repeated re-bakes), in
`derived-bakes-049a`:

| | Nodes | `document_bytes` | Journal bytes |
|---|---|---|---|
| 048B writer, at the first rejected edit | 12 | 3,728,890 | 3,721,670 |
| After migration (3.68 MB of payload references removed) | 12 | 40,642 | 33,590 |
| 049A writer, same sequence | 23 (all accepted) | 63,657 | 56,607 |

An incremental save does not shrink the physical file, because SQLite keeps
free pages (the known 045A limit). Saving to a new file does.

## Limits

- Whether a re-bake reproduces the digests on another solver build has not
  been tested. A different build is expected to report a mismatch, not to
  substitute its frames.
- The amber "re-baked frames differ" state is covered by unit tests only, not
  by a Studio capture.
- The migration needs a saved `.ark` path for its backup. Unsaved documents
  are refused.
