# 045A - save capacity, journal visibility and live client activity

Runtime 0.9.46 and iteration identity come from `release.json`. Phase **A**
(trust) is the principal focus. Milestones **A.02** and **D.02** remain
**Parcial**. The scopes below are **Verificado no escopo local** as described
under Verification. No performance, cost or design-quality claim is made.

The work comes from a read-only audit of one user project opened with the 044B
runtime. Only aggregate observations are retained here; the project itself
stays local and was not edited, saved, committed or packaged.

| Observation in the audited project | 045A response |

## Saved geometry over capacity (A.02)

Saved native geometry stays an optional cache. When an entry would exceed the
64 MiB per-entry limit, the 128 MiB total or 8192 entries, it is omitted in
document order and the authoring save proceeds. Omitted bodies are evaluated
from authoring on the next open, as when no cache exists. Authoring is never
truncated, and the 4 MiB authoring limit is unchanged.

`doc_save` returns `saved_geometry` with `status` `saved` or `partial`,
`entries_saved`, `bytes_saved`, `entries_omitted`, `bytes_omitted` and
`capacity_bytes`. Studio's status bar reports a partial save. A failed save
now carries its reason, for example a missing folder, instead of only
"Could not save document". [Formats](../FORMATS.md).

## Iteration journal visibility (A.02)

The journal keeps its contract: 512 nodes, 4 MiB, immutable nodes and no
silent pruning. 045A only makes consumption visible:

- `history_info` adds `max_nodes`.
- Commit receipts add `history_capacity` once the journal reaches 384 nodes or
  the document 3 MiB.
- A `doc_apply` made only of `assembly.drive` commands that returns the
  assembly exactly to its state before the previous iteration adds
  `history_round_trip` with a hint.

Assembly onboarding, the motion topic and the `assembly_info` description
direct temporary checks to `assembly_info{drive|sweep}` or to `doc_preview`
with `assembly.drive` plus `snapshot{candidate_id,expected_revision}`.
[Iteration history](../ITERATION_HISTORY.md).

## Live MCP client activity (D.02)

Every call through Studio's live bridge (`ark-mcp --connect`) now declares
`{kind:"client",id:"live_mcp"}`, not only writes. The session records a client
call in the project activity ledger when it commits authoring or fails:
a rejected call, a `query_batch` with a failed row, or a rejected preview.
Successful reads are not recorded, which bounds ledger and document growth.
Receipts carry `activity_id` and `pending_feedback_ids`, and the client rates
its own records with `tool_feedback`. Pending client feedback never blocks a
team role. Human Studio edits stay outside the ledger. The client's token use
remains unknown unless it reports `usage_record`.
[Project activity](../AGENT_ACTIVITY.md), [live connection](../CODEX_CONNECT.md).

## Verification

All results below come from a **local diagnosis build**: llvm-mingw clang with
the local, unpatched MinGW OCCT 8 SDK (`ARK_ALLOW_UNPATCHED_OCCT=ON`) on one
Windows machine. It is not the release toolchain (MSVC with the verified
`ark-offset-001` SDK), so a release CI run is still required.

- **New checks:**
  - `native_cache-032d`: byte and entry capacities omit later entries without
    throwing; a bounded subset saves and reopens; the save receipt reports
    saved geometry; a failed save states its reason.
  - `reactivity-activity`: a client's successful read is not recorded; its
    commit, stale write and failed batch are; it rates its own record; human
    edits stay outside the ledger.
  - `assembly-manipulation-tools`: an exact drive round trip is reported with
    the read-only hint, a new pose is not; `max_nodes`; assembly onboarding
    names `snapshot{candidate_id}`.
  - `iteration-history`: 384 real commits; the warning appears at the 384th
    node and not before.
- **Suite:** the same 146 CTest tests ran on the unmodified 044B tree and on
  this branch, each built with the same toolchain. Both passed 143/146. The same
  three fail on both: `distribution-fixtures` (needs `cmake` on `PATH`), and
  `native-solid` and `native-surface` (offset and C2 loft checks that depend on
  the verified OCCT patchset).
- **Studio selftests** (opt-in live tests): `realtime-ui`, `history-ui`,
  `recovery-ui` and `team-blockers-ui` passed on both trees; `connectors-ui`
  failed identically on both (exit 500). Captures were inspected.
- **MCP end to end:** a standalone `ark-mcp` session confirmed that
  `doc_preview` with `assembly.drive` plus `snapshot{candidate_id}` renders the
  opened pose while the journal stays at one node, and showed the
  `saved_geometry` and failed-save receipts.
- **Live bridge end to end:** a temporary Studio with isolated settings and
  `ark-mcp --connect`, with no actor declared by the caller: every call carried
  `live_mcp`; the commit, the stale write and the failed batch were recorded,
  the successful read was not, the client's rating was accepted, and the
  journal node kept the `live_mcp` attribution.

The Studio status text for a partial save and an actual cache above 128 MiB
were not exercised; the capacity rule is tested with injected limits.

## Not established

- The journal still rejects every edit at 512 nodes or 4 MiB. Compaction or
  an explicit new-baseline operation needs a separate design decision.
- Which cache entries to keep is a document-order rule, not a measure of
  recompute cost.
- Free pages left by incremental saves are not reclaimed; the audited file had
  18.2 MiB (about 15%) of free pages.
- A host-side rejection that never reaches the session, such as the
  compaction guard before a write, still leaves no activity record.
- `Document capacity exceeded` still does not name the limit reached.
