# 003D — recuperação de falhas temporárias do serviço

Data: 10-10-2026. Sequência global: 003. Fase principal: D.
Versão técnica: 0.9.4. Baseline: 002B / `2453974`.
Milestones D.02/D.04 permanecem parciais.

## Problema reproduzido

O utilizador observou `ChatGPT Responses HTTP 503` depois de uma chamada
`team_context`. Resume permitiu continuar. O transporte anterior transformava
qualquer HTTP não-200 numa exceção genérica, levando a equipa diretamente ao
estado de continuação manual. O screenshot não contém o corpo/código do erro;
não permite atribuir a causa a capacidade, routing ou verificação de utilização.
Além disso, o leitor HTTP ativava o parser SSE para qualquer status do endpoint
Responses. Um erro HTTP em JSON podia perder o corpo antes de chegar ao
diagnóstico. A seleção SSE passa a exigir status 200; os erros passam pelo
checker tipado, sem expor o corpo bruto, tokens ou credenciais.

## Contrato de recuperação

- Repetir apenas um pedido HTTP elegível que falhou antes de uma resposta aceite.
- Conservar o pedido e o histórico, incluindo recibos das operações já concluídas.
  Não executar novamente ferramentas CAD durante a repetição de transporte.
- Esperar com backoff e respeitar `Retry-After`. Não tentar mais cedo quando o
  servidor pede uma espera superior ao limite suportado; deixar retoma manual.
- No máximo três novas tentativas por pedido, com base de 1/2/4 segundos e jitter.
  Esperas pedidas pelo servidor acima de 30 segundos deixam o pedido adiado.
- Mostrar a tentativa na interface e permitir Cancel durante a espera.
- Conservar o modelo, esforço, autenticação e preferências da equipa.
- Não tratar limites de conta, créditos ou autenticação como falhas temporárias;
  não repetir automaticamente streams interrompidos depois de output.

O limite de tentativas aplica-se à recuperação de uma falha de transporte,
não ao número de turns ou tokens permitido aos agentes.
