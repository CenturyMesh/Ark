# 038B - native failure investigation and retained query recovery

Runtime 0.9.39 is defined by `release.json`. This iteration addresses
**A.03/A.04/A.05/B.01/B.02/D.02/D.04**. Status: **Em curso**. The portable recovery
contracts below are verified locally; native recovery and distribution remain
open. No drawing format change is required.

## Observed failures

A 037D session rejected an initial smooth spline loft, then successfully created
a replacement loft. A subsequent shell operation rejected with `BRep_Tool:: no
parameter on edge`. The shell request returned in about 189 milliseconds; the
continued provider activity was not a stuck kernel worker. At the captured
checkpoint the document remained at revision four while 185 provider responses
reported a lower bound of 10,351,691 tokens. No cost or matched speedup claim is
made. Exact baseline/request bundles remain private and are replayed without a
model in isolated sessions.
The later partial receipt stopped at the same revision with 11,220,217 reported
tokens, 199 reported responses and three responses missing final usage. Those
unreported tokens remain unknown; investigation did not start another provider run.

Follow-up query batches requested absent fields such as `plane` and `references`.
The projection exception discarded other successful rows from the same batch.
The coordinator also considered only the outer result status, while activity
accounting suppressed nested calls. Thus a mixed batch could hide a rejected
query or clear an unrelated failure.

## Recovery contracts

- Structural batch validation still completes before any query runs. Each query
  executes once. Missing projected fields now produce `QUERY_BATCH_FIELD_MISSING`
  in that row, retaining the observed result, available fields and executable
  recovery arguments. Other query results survive intact.
- The coordinator checks batch row association before resolving failures. An
  unrelated successful query cannot clear another rejected reference or object.
  A successful current-revision retry resolves a revision conflict with explicit
  or omitted read `expected_revision`; old receipts cannot do so. Corrected
  previews and atomic-write aliases preserve their existing recovery contract.
- Activity records distinguish success, partial failure and all-failed batches,
  with bounded diagnostics and actual row counts. The original MCP envelopes and
  successful results remain unchanged.
- Request projection retains the actual recovery packet across subsequent reads,
  as historical data. A successful matching query retires that packet. Original
  host history remains exact and observed historical revisions do not authorize
  writes.
- A changed selector for the same object may explicitly supersede an earlier
  rejected read through `team_report_task` with `state:in_progress`. The host
  requires both exact query identities, a concrete reason, that role's later
  successful receipt and a fresh revision check in the same project. The whole
  resolution list is validated before clearing any failure. Writes, previews,
  completion and BOM/feedback gates cannot be waived this way.

The first focused Team test run exposed a null access in a new test's diagnostic

The QR-only candidate native integration passes **133/135** registrations.
The two failures are the new offset-regularity and multi-curve concatenation
regressions, whose patches are not in that candidate SDK. Loft lifecycle and
analytic controls pass, as does activity/persistence integration. This is an
intermediate dependency configuration, not a qualified distribution. The isolated
Studio/MCP live edit, save/reopen and undo integration also passes. No new paid
provider run was used.

## Native gates still open

Both original failures reproduce with the unchanged SDK and leave the scratch
document unchanged. Extending an edge parameter range alone removed the first
shell exception but produced invalid B-rep and failed volume conservation; that
candidate was rejected. The current investigation follows edge regularity,
intersection-point consistency, approximation constraints and shared-parameter
curve assembly. A tangent at a continuity boundary was evaluated from the wrong
side of its active interval. Correct interval-local derivatives restore the
first approximation family's existing tolerance, but expose a separate
multi-curve concatenation error. Full shell and downstream split acceptance
remain open; numerical acceptance thresholds are unchanged.

The initial loft has valid, closed, planar input wires. Its variational solver
formed normal equations that lost the positive regularizer numerically. A
private QR implementation instead uses the original least-squares factors and
the same constraints and objective. The frozen request now replays successfully,
produces valid exact B-rep and survives save/reopen. Independent high-precision
and analytic controls support the scoped correction, including translated
profiles. The patch is still a candidate pending integrated native regressions.
Correctly recomputed geometry can differ from the original inaccurate solver.

Native dependency changes use separate source/build/SDK copies and recorded
module hashes. An overlay is explicitly labelled `local-sdk-overlay`, not a
clean full-SDK rebuild. Public packaging rejects candidate manifests. Source
patches, dependency notices and the exact final runtime inventory remain release
gates under **A.05**.
